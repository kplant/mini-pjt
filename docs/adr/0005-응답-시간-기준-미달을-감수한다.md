# 응답 시간 10초 기준은 일부 요청에서 넘는 것을 감수한다

SERVICE.md 5번은 모든 요청이 10초 안에 끝나야 한다고 정했습니다. 1라운드에서는 회차마다 25요청 중 5건이 넘었습니다. TASKS 5-4-1에서 trace에 구간별 시간을 남겨 재 보니, 응답 시간의 약 96%가 차례로 이어지는 모델 호출이었고 호출 한 번이 약 2.5초였습니다. Supervisor 라우팅 1번, 하위 Agent의 도구 선택과 답변 작성 2번이 기본이라 7~9초가 되고, 일정을 조회한 뒤 바꾸는 흐름은 호출이 4번이라 평균 9.5초입니다. 프로세스의 첫 요청은 모델 클라이언트 생성과 Chroma 열기로 약 5초가 더 붙습니다.

줄일 방법은 세 가지였지만 모두 쓰지 않습니다. Supervisor를 Haiku로 바꾸면 라우팅이 약 1초 빨라지지만, TASKS 3-2에서 라우팅을 잘못 보낸 일이 있어 정확도를 우선해 Sonnet을 유지합니다. 첫 요청의 지연은 서버가 뜬 뒤 한 번뿐이라 허용합니다. 조회 후 변경 흐름의 호출을 줄이려면 도구 설계를 바꿔야 해서, 이후 리팩토링 때 검토합니다.

그래서 10초 기준은 '도구를 두 번 부르는 흐름과 첫 요청에서는 넘을 수 있다'는 한계로 받아들이고, 라운드 리포트와 README에 그대로 밝힙니다. 다시 줄여야 하면 위 세 가지가 출발점입니다.

TASKS 5-5에서 1~3라운드를 모아 보니, 모델 호출이 3번인 요청도 그중 한 번이 길어지면 10초를 넘는 경우가 있었습니다(2·3라운드 6건, 길어진 호출 3.7~6.2초). 모델 호출 한 번의 시간은 486회 기준 중앙값 2.48초, 95번째 값 3.48초였고, 같은 문항의 다른 회차는 10초 안이었습니다. Bedrock 응답 시간의 변동이라 코드로 막을 수 없어, 이 경우도 감수 범위에 넣습니다. 답변 길이를 줄여 마지막 호출을 짧게 하는 방법은 답변 품질 지표에 영향을 줄 수 있어 시도하지 않았습니다.
